# Contribution Publishing Workflow

Contributors share ideas on the website, Moderators verify (and may improve) them, Admins preview and publish them, and published ideas appear on the public **Community Ideas** page. Only an Admin can publish, and an idea becomes *Published* only after the public record has been read back and matches the approved version.

Behaviour follows the implementation prompt (v2) and the demo `RV-Web-Demo-ContributionWorkflow-v3.html`, with the project decisions below. The standalone demo built from the same files is [`docs/reference/contribution_demo.html`](../reference/contribution_demo.html); it opens by double-click and runs on mock data.

## Where everything lives

| Part | Where | Built with |
|---|---|---|
| Share Your Idea (form) | WordPress, plugin `robovalley-contribution`, shortcode `[rv_contribution_form]`, page `/share-your-idea/` | `public/cw/js/form.js` |
| Community Ideas (public) | WordPress, same plugin, shortcode `[rv_community_ideas]`, page `/community-ideas/` | `public/cw/js/site.js` |
| Moderator Workspace | admin portal `/admin/workspace` (administrators and moderators) | `public/cw/js/moderator.js` |
| Admin Approval Dashboard + Publish Preview | admin portal `/admin/approvals` (administrators only) | `public/cw/js/admin.js`, `preview.js` |
| My Contributions (read-only, every portal) | `/my-contributions` (`/dashboard/contributions` redirects there), in the navigation of every portal: `src/lib/memberNav.ts` (Member portals) and `src/app/admin/_components/nav.ts` (admin and moderator) | `public/cw/js/mine.js`, `src/lib/cw/mine.ts` |
| Data and rules | the app's database (migrations 027 and 028, tables `cw_*`) and API routes under `/api/cw/` | `src/lib/cw/*` |

Decisions: one source of truth (the app's database, no WordPress tables or roles); admin = `users.role = 'admin'`, moderator = `users.is_moderator`, contributor = a signed-in member; no Bootstrap (one `.rv-`-scoped stylesheet for WordPress, `admin.css` plus `src/app/_cw/cw-portal.css` in the portal); name and type come from the profile (our 12 stakeholder roles); one optional sector from Sector Forms plus "Not sure", with the robot type list following it; attachments up to 4 MB, JPEG/PNG/PDF, type read from the file's bytes; older contributions stay in the existing Moderation page; Request Changes goes back to the Moderator (contributors never edit after submitting).

## One copy of every rule

`public/cw/js/` holds plain ES modules used by **the browser and the server**:

| File | What |
|---|---|
| `lists.js` | master lists, statuses and their labels and badge classes, field labels, filters, limits, every message, **`PUBLIC_NAME_DISPLAY`** (the one setting for how contributors appear publicly) |
| `rules.js` | slug and resource ID, validation, the status machine (`nextStatus`), history wording, the public card record (`toPublicRecord`), file-type sniffing |
| `utils.js` | escaping, word diff, dates, DOM helpers |
| `card.js` | **the** public card, used by the Publish Preview, its downloadable `.html` and the live Community Ideas page |
| `api.js` | `RestAdapter` (production) and `MockAdapter` (demo only; it applies the same rules) |
| `form.js`, `moderator.js`, `admin.js`, `preview.js`, `site.js`, `review.js`, `dialog.js` | the screens |

The server imports them through `src/lib/cw/shared.ts`. The portal loads them at run time (`src/app/_cw/CwMount.tsx`, not bundled). The WordPress plugin ships them as **one** generated script, and the demo inlines the same bundle. Both are generated by:

```
node scripts/build-contribution-workflow.mjs          # writes the plugin script, the plugin stylesheet copy and the demo
node scripts/build-contribution-workflow.mjs --check  # fails if any of them is out of date
```

`tests/cw-build.test.ts` fails when a generated file is out of date.

## Data (migrations 027 and 028, additive, safe to run twice)

`cw_contributions` (ids from **1025**, shown as `RV-1025`; `original`, `resource`, `reference_links`, `kind` and the contributor are written once and a trigger refuses any change), `cw_contribution_versions`, `cw_contribution_feedback`, `cw_contribution_history` (all append-only), `cw_contribution_attachments` (private), `cw_public_contributions` (one row per published idea, upserted by id; the only table the public page reads). Rollback: `db/rollback/027_down.sql` (refuses while ideas exist).

**028** (the decided open points) widens three of 027's checks under the same names: status `unpublished`, the published rule for Unpublished ideas, and the feedback types `decline` and `reopen`. 027 itself is never edited. Before 028 the app keeps working: a Moderator's decline is stored as a rejection and Unpublish and Reopen answer "not set up yet". Rollback: `db/rollback/028_down.sql` (refuses while an idea is Unpublished or a decline or reopen reason exists).

## Statuses

Submitted → Under Moderator Review → Moderator Draft → Pending Admin Approval / Resubmitted for Approval → Publication In Progress → Published, plus Changes Requested, Publication Failed, Rejected and **Unpublished**, as in the spec's table with the decisions below (`rules.js: nextStatus`, the one transition function). Every transition not listed is refused by the server. Every change locks the row and checks `row_version` (409 when someone else changed it first) and appends a history line with the real signed-in person's name.

## API (`src/app/api/cw/`)

| Route | Who | What |
|---|---|---|
| `GET form-config` | public (rate limited) | sectors and robot types from Sector Forms |
| `GET me` | public (rate limited) | signed in? name and type from the profile; reviewer? |
| `POST contributions` | signed-in member (not a reviewer) | submit (multipart: `data` + optional `attachment`) |
| `GET mine` | signed-in member | own ideas, read-only |
| `GET review?view=workspace\|approvals&filter=` | reviewers / administrators | lists, counts, older-form count |
| `GET review/[id]`, `POST review/[id]` | reviewers; Admin actions administrators only | detail; actions `open`, `save_draft`, `reset`, `send_request`, `decline`, `preview`, `admin_edit`, `request_changes`, `reject`, `publish`, `unpublish`, `reopen` |
| `GET review/[id]/attachment` | reviewers | the private attachment |
| `GET public` | public (rate limited) | published ideas only |

## Notifications

Sent through Resend after the change is saved (never blocking it): a new idea → the Moderators (the Admins if there is none); a publishing request or resubmission → the Admins; changes requested, or an idea reopened → the idea's Moderator; published or rejected → the contributor. Unpublish sends no email. Links use `APP_URL`.

## "Contribute to this sector" everywhere (the injection hooks: do not remove)

| Where | What | The hook |
|---|---|---|
| Website, every Robots by Sector page (also new ones) | "+ Contribute to this sector" next to the title, sticky top-right; a sticky button on every field | `frontend/wordpress/plugins/robovalley-contribution/sector-buttons.php` (`the_content` at `PHP_INT_MAX - 10`, late enqueue, footer fallback) loading `assets/js/rv-sector.js` |
| The shared component (one copy) | the header, the sector page, the cards, the field buttons, persistence (MutationObserver) | `public/cw/js/sector.js`, `public/cw/js/fields.js`, `public/cw/sector.css` |
| App: Moderation by sector, Sector forms | the same header (title + button), server-rendered from the same function | `src/app/_cw/SectorHeader.tsx` (calls `sectorHeaderHtml`) |
| App: every Member portal's Sectors (list + one sector) | the same sector page component (header + cards + field buttons + "Suggest a field") | `src/app/dashboard/sectors/*` mounting `public/cw/js/sectors.js`; the nav item in `src/lib/memberNav.ts` |

A field is an element with `data-rv-field="<id>"` (the contract for other plugins), a top-level section of the page content (Elementor sections and containers, Gutenberg groups, `<section>`, `.rv-rt`), or a selector added with the `rv_contrib_field_selectors` filter. The buttons open the live contribute flow with `?sector=` and `?field=` (and `resource_path`, `resource_url`, `return_to`); the form fills in the sector, the robot type when the field is one, the resource, and offers the way back after sending. The only way to hide a field's button: Settings > Contribution workflow > "Fields without the button". `tests/cw-fields.test.ts` and `tests/cw-sector.test.ts` fail when a sector page or a rendered field has no button.

## Demo data (local and preview copies only, never production)

`scripts/seed-contribution-demo.mjs` fills a local or preview copy so no page is empty:

- 4 sectors with 3–5 fields (robot types);
- users for every role;
- at least 2 ideas in every status, with feedback on the rejected ones;
- current-form items in every status, with replies;
- the moderation queue, the workspace, the approvals, Community Ideas and every demo user's My Contributions.

```
# PowerShell: $env:DEMO_MODE = "1"   (bash: export DEMO_MODE=1)
npm run seed:contribution-demo -- --expect-db <database name>                    # dry run: the plan, connects to nothing
npm run seed:contribution-demo -- --expect-db <database name> --apply            # add it (safe to repeat); prints the demo passwords once
npm run seed:contribution-demo -- --expect-db <database name> --reset --apply    # remove ONLY the demo records
npm run seed:contribution-demo -- --expect-db <database name> --preview-host <host> --apply   # a preview database (that exact host only)
```

It is never run automatically. It refuses unless every one of these holds:

- `DEMO_MODE=1` is set;
- neither `NODE_ENV` nor `VERCEL_ENV` is `production`;
- `--expect-db` matches the database;
- the database is local, or exactly the `--preview-host`;
- every migration up to 029 is applied;
- the database holds at most 25 real accounts (more looks like a live site).

How demo records are told apart:

- users: `@demo.robovalley.test`;
- new-workflow ideas: `cw_contributions.is_demo` (migration 029; it hides nothing);
- current-form items: ids from 8,000,000,000,000. `contributions.is_demo` already means "hidden from the counts and the moderation queue", which would leave those pages empty.

The WordPress side of the demo (sector pages with a suggested field, a plugin field, a long address and a wide table) is made by `tools/contribution-e2e` on its own local WordPress. The standalone demo has all of it.

## Switch-over

WordPress: **Settings > Contribution workflow**, one checkbox, OFF by default. ON makes both pages public, redirects the current form's pages to `/share-your-idea/` (301, keeping `?sector=`, never cached) and points "Contribute to this sector" at the new form. OFF (or deactivating the plugin) restores today's behaviour exactly. The current form (`rv-contribution-v2`) is never modified.

## Tests

`tests/cw-*.test.ts`: rules (unit), migrations 027 and 028, submit, the Moderator and Admin APIs, publishing (including failure and retry), notifications and spam protection, each screen in a DOM, accessibility, the standalone demo, the generated files and the plugin. `tests/cw-merge-safety.test.tsx` runs the code against a database without 027, 028 and 029.

`tools/contribution-e2e/` (run by hand, needs Docker; see its README): the end-to-end check on a throw-away local stack (the app, its own Postgres, a WordPress with Astra and both plugins, a headless browser behind a safety gate), the WordPress lifecycle (switch, deactivate, reactivate, version change, uninstall, reinstall) and every migration twice on a fresh database. Nothing there can reach a live database or website.

## The spec's open points, as decided (27-11-2026)

| Point (spec section 15) | Decision | Where |
|---|---|---|
| Unpublish | Admin only, on Published items. The public card is removed and the status becomes **Unpublished** (own badge, listed under the Admin's "Published" filter), logged in history. Publishing again is the normal flow (preview, then publish) and updates the same card: never a duplicate. | `nextStatus("unpublish")`, `store.ts` (one transaction), `admin.js` |
| Edit after publishing | "Edit Before Publishing" also works on Published and Unpublished items. It makes a new version that needs a new preview; the live card changes only when the Admin publishes again. A failed update keeps the earlier card live and the idea Published (with the error shown and Retry). | `nextStatus("admin_edit" / "publish" / "publish_fail")`, `publish.ts` |
| After Rejected | No appeal by contributors (they can always share a new idea). The Admin may **Reopen** a Rejected item (reason required): back to Under Moderator Review, with a history line, and the Moderator is emailed. | `nextStatus("reopen")`, `store.ts`, `admin.js`, `moderator.js` |
| A Moderator's decline | Admins see it in the "Rejected" filter (who declined, the reason and when; an Admin's rejection is shown as such) and can reverse it with Reopen. | feedback type `decline`, `listContributions`, `admin.js` |
| Earn (18+) | Not offered to a minor in the form (`users.age_category`) and refused by the server if sent anyway; a Moderator cannot set it on a minor's idea and an Admin cannot preview or publish such a version, each with a clear message. | `rules.js: earnBlocked`, `form.js`, `moderator.js`, `publish.ts` |
| Admin edits | Title and Description only, as in the demo. | `store.ts: admin_edit` |
